# Proto P2/P3限定反映

基準2856fd8（P1）。P2は期限境界の受付拒否・同じ配信の回答上書き防止。
P3はFCM呼出し前の送信権保存・結果不明時の自動再送停止。完全な一回配送を保証しない。
過去の研究データの補正・移行処理は含めない。Web/Firebase設定は変更しない。

## 要確認通知の運用

上松がSSHで正しい接続先uva.alchembright.com、~/kirokun-protoであることを確認し、
`bash ops/proto-notification-review.sh list` を配信後・再起動後に実行する。
出力はレコードID・通知状態・日時のみ。pendingは処理途中の場合もあるため、稼働中の瞬間値だけで失敗とは判定しない。
review_requiredまたは停止後も残るpendingは、自動再送しない。実機受信状況と配信時刻を確認する。
未受信と断定できない場合は、重複の可能性を説明して上松が判断する。

再送はAPIを停止してから対象1件・種別・観測済みStartedAtを指定する。
作成経緯を確認したhiroki_u作成データだけを、環境proto、createdBy=hiroki_u、records=[{collection,id}]のJSONに記録しops/state/へ置く。
DBに作成者属性がないため、名前から所有を推定してはならない。他研究者分は承認なしに対象表へ加えない。
`bash ops/proto-notification-review.sh requeue assignments ID publish ISO /review/state/対象表.json`
グループはassignmentresultsの対象者別IDを指定。API停止確認、既存受付日時なし、期限内、期待状態一致のときだけ1件を再待機へ戻し、履歴を残す。
この操作ではFCMを呼ばない。予約が通常の通知検索時間範囲内にあることを確認してからAPIを起動する。
範囲外なら時刻を勝手に変更しない。現状は手動確認であり、自動監視メールは未実装。

## 配備・切戻し

直前バックアップと隔離復元を検証し、P1実イメージ・compose・設定・DB件数を保全する。
必要なコンパイル済み4ファイルだけを現行イメージへ重ね、APIだけを交換する。依存更新なし。
他研究者のデータを補正する処理なし。検証書込みは作成経緯が明確な上松用データだけ。
配備後health、実ファイル差分、DB件数、読取専用要確認一覧を確認する。
起動/認証/保存障害・予期しない通知を停止基準とする。
切戻しはAPI停止→要確認通知照合→保全composeで旧API起動。未確定通知がある場合、旧版は送信権を無視するため、通知を止める承認と対処が必要。DB全体を復元して新しい回答を消さない。
P2切戻しは期限後回答や上書きを再許容するため、調査再開は別判断。
