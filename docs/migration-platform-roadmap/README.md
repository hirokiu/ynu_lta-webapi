## 段階1：devで共同研究者の管理画面確認

1. 対象者は上松と共同研究者2名。既存アカウントの実際のログインメール・Firebase UIDと必要な閲覧範囲を特定する。現行の管理者名ハードコードだけに依存せず、dev用の許可対象をサーバー側で限定する。未認証・許可対象外のAPIを拒否する。管理者権限が研究全体に及ぶ現行仕様を確認し、対象データと整合させる。
2. 通知停止を維持し、通知送信箇所でも停止を強制する。devの配信操作は無効化または明示的に対象外として扱い、実配信テストと混同させない。Firebase共有中はアカウントの追加・パスワード変更など共有認証へ作用する操作もUI確認の対象外。
3. 上部の常時表示：**「管理画面の確認用環境です。アプリとは連携せず、通知は送信されません。登録・編集内容はproto／現行環境へ反映されません。検証データは初期化される場合があります。」**
4. HTTPSと指定者限定アクセスを検証して公開する。前回の自動承認レビューで本番コピーの公開が停止されているため、今回明確になった目的・対象者・範囲に基づき公開操作を再審査し、通過後に有効化する。設定準備は公開済みを意味しない。
5. 確認項目：ログイン、Survey一覧の10/20/50/100件切替、設問テンプレート保存・読込・編集・新規保存、既存コピー回答の選択/期間/全件出力、待機表示、操作文言。devにはアプリから新回答は到着しない。

## 段階2：protoへ移行して運用開始

1. 新サーバーにdevと別Compose project・DBボリューム・バックアップ先を用意。proto.kirokun.alchembright.comのDNSとHTTPSを準備。protoはdev DBを昇格させず、旧環境の正本から復元する。
2. 現行のWeb/API全ホスト名・パス・ポート、iOSストア版と現行Android APKの接続先、Firebaseに設定されたURL、証明書、他サービスを棚卸しする。アプリの実バイナリー/実機でも確認する。
3. 新Webの正式な入口はprotoとする。既存アプリが旧API URLを使う間は、そのホスト名もDNSで新サーバーへ向け、新サーバーが同じAPIパスを直接処理する。APIのPOSTを単純リダイレクトに依存させない。旧Webのリンクも必要期間維持する。旧ドメインの保持と旧サーバー契約の保持は別である。
4. 事前復元でログイン・一覧・CSV形式・時刻・旧アプリとの互換性・復元手順を確認。通知はこの時点では無効。
5. 最終切替：利用者に時間を共有→旧Web/API書込と定期配信処理を停止→最終バックアップ→protoへ復元→件数・整合性確認→protoと旧互換ホストのDNS切替。旧側では新しい書込を受けず、DNSキャッシュ期間の分散書込を防ぐ。端末の未送信回答にも注意する。
6. 予約と期限切れ通知の残存を再確認。devは停止状態のまま、protoだけで必要な配信処理/通知を有効にする。通知なしの移行確認と実通知試験を分け、共同研究者の端末で行う。現在のNOTIFICATIONS_ENABLEDは回答準備も止めるため、有効化条件を記録する。
7. proto Web・既存アプリで取得/回答/出力を確認。バックアップ03:00 JST、日曜03:30の再起動、保持期間を環境別に設定し、復元テストと定期実行を確認。旧サーバー側タイマーを停止し二重実行を防ぐ。
8. 検証したコミット・イメージ・バックアップ日時・DNS切替時刻を記録。切戻し先を保持。新環境で書込が始まった後の切戻しは単なるDNS復帰にせず、新規回答の保全・同期を先に行う。

## 段階4：新プラットフォームの本番運用

新たな実調査を始める前に、本番専用Firebase/DBを新規作成し、以下の権限・招待機能を整える。既存資産はprotoとして保存し、設問テンプレートを選んで取り込む。既存回答や利用者を移す必要がある場合は、目的・対象・ID対応を別に定義して移行する。新Firebaseへ切り替える正式アプリ更新・再ログイン手順も必要であり、サーバー側だけでは完了しない。

### 権限モデル

|役割|可能な操作|範囲|
|プラットフォーム管理者（上松）|研究プロジェクト開設/停止、研究者招待、役割設定、利用状況・監査・運用管理|全体。個々の回答の閲覧は必要時に理由を残して実施する設計|
|研究者・アンケート作成者|Survey作成/編集/配信、回答出力、担当プロジェクトへの回答者招待、自分が配信対象のSurveyへの回答|自分の所属研究プロジェクト内。他プロジェクトの利用者・回答は扱えない|
|回答者|招待を受けたプロジェクトへ参加、割り当てられたSurveyへの回答|自分に許可されたSurveyのみ。他人の回答、作成・配信機能は利用不可|

研究者による利用者追加は原則回答者招待。研究者役割の付与は上松、または上松が明示的に委任したプロジェクト管理者に限定する。研究者がプラットフォーム管理者へ自己昇格できない。1人が複数研究に参加し、研究ごとに異なる役割を持てる設計にする。「Survey管理画面作成可能」は、自分の研究プロジェクトに管理領域を持てる意味とし、研究ごとのコード/サーバー複製は前提としない。

### 招待と登録

- Firebaseコンソール操作を研究者に開放せず、Web/APIから権限確認済みの招待を発行する。
- 招待にプロジェクト・宛先メール・役割・有効期限を結び付け、推測困難な単回トークンを発行。取消・期限切れ・再送・二重利用を扱う。受諾時に宛先所有を確認し、既存アカウントなら安全に所属を追加する。
- Firebase UIDで本人を識別し、プロジェクト所属・役割はサーバーが管理する。現行の文字列管理者一覧やメール末尾除去への依存を置き換える。画面を隠すだけでなく、すべての読取・更新APIで所属と役割を確認する。
- パスワードは招待された本人が設定し、研究者には表示しない。研究からの脱退・招待取消と、共有アカウント全体の削除を区別する。
- 招待メール送信用サービス・送信ドメイン、到達確認、回数制限、監査記録、パスワード再設定を用意する。メール送信機能の実装と、今回の会話から研究者にメールを実送信することは別の操作とする。

### 管理画面と実装順

1. UID・プロジェクト・所属・役割のデータモデルとAPI権限テスト（研究をまたぐアクセス拒否）。
2. 上松のプラットフォーム管理画面：プロジェクト/研究者/役割/停止・再開/監査。
3. 研究者の管理画面：回答者招待・状態確認・再送・取消、Survey管理。
4. 回答者の招待受諾・登録・ログインとアプリ連携。
5. 新本番Firebase/DB、正式アプリ、復元・通知・権限の受入検証を完了して新調査開始。

視覚的な設問エディターや他形式からの変換は、この段階の別機能として優先順位を決める。現行JSONテンプレートの互換性を維持する。
