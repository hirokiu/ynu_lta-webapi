# KIROKUN 開発・本番の分離と運用手順

2026-09-17。設計・運用計画。以下の分離は未実施。既存アプリ、本番DB、Firebaseは変更しない。

## 現状と3つの懸念

- dev.kirokun.alchembright.com は新サーバーを名前解決するが、HTTPS入口は未起動。Webは127.0.0.1:8080のみで、SSHトンネルによる確認用。DNS設定だけで利用者には公開されない。
- 確認用DBは2026-09-17 18:57 JSTの本番コピー。本番で増えた回答は反映されず、確認側の変更も本番へ同期されない。分離後も独立したデータになることは正常な仕様。
- WebとAPIは本番用Firebaseを共用。名前が `ynu-lta-dev` でも現役の本番用として扱う。別アカウント名だけでは認証・通知基盤の分離にならない。
- NOTIFICATIONS_ENABLED=falseで定期実行そのものを止めている。src/api.tsでは同じ処理内でCreateImpendingResultObjectsと通知検索を呼ぶため、通知以外の回答準備も止まる。通知なしでも通常の配信・回答が動くよう分離が必要。
- コピーDBに本番利用者の端末トークンが含まれる。現状で通知を有効化してはいけない。CloudMessageService.sendMessage自体にも送信禁止判定を追加する。
- 本番アプリの接続先はWebの新ドメイン作成だけでは変わらない。開発APIを参照する専用ビルドが必要。Surveyを作るたびにアプリ更新が必要なわけではなく、既存の設問形式に対応していれば、配信対象・期間・回答準備・API取得が揃うことで回答可能。新しい設問種別や非互換形式ではアプリ更新が必要。
- 調査したiOS設定では既存Bundle IDはcom.alchembright.dev.ynu-lta-dev。ストア配布バイナリーの実際のAPI接続先は分離作業時にビルド設定・実機通信で再照合する。

## 目標構成

|項目|開発・利用者テスト|本番|移行検証用コピー|
|---|---|---|---|
|Web/API|dev.kirokun.alchembright.com と /api|移行当面は既存URLを維持。将来のkirokun配下名は別途決定|非公開・SSH経由|
|アプリ|KIROKUN Dev、別Bundle ID / Android applicationId|既存IDを維持|通常接続しない|
|配布|iOSは別App Store ConnectアプリのTestFlight、Androidは開発専用APK等|現行iOSストア版、Android現行配布版|なし|
|Firebase|新規の開発専用プロジェクト|既存ynu-lta-devを継続|必要時のみ本番認証、通知禁止|
|DB|架空利用者・テスト回答のみ|実研究データ|本番の限定コピー|
|通知|開発アプリから登録されたトークンだけ|本番端末のみ|常時禁止|
|バックアップ|開発用保存先・保持期間|本番用保存先・復元確認|アクセス限定・用途終了後の削除方針を決める|

同一サーバーでもCompose project、DB/証明書等のボリューム、秘密鍵、ポート、バックアップ、タイマー、資源上限を環境別にする。DB/APIポートは外部公開しない。*.kirokunのDNSだけで環境は自動生成しない。登録したホストだけHTTPS入口で転送する。負荷試験は本番同居サーバーを圧迫しない範囲で実施する。

## 分離手順（順序）

1. 既存の確認用コピーは非公開の移行検証用として保持。実データは新しいdevへ流用しない。既存の本番接続先・配布アプリを記録し、移行作業と開発環境作成を別作業として管理する。
2. 開発専用Firebaseを作成し、Web・iOS・Androidアプリを登録。メール認証設定、必要なWeb認証ドメイン、開発用サービスアカウント、iOS通知用APNs設定を用意する。既存本番Firebaseを改名・削除・転用しない。
3. APIのFirebase設定・管理者一覧・認証メールの扱いを環境設定にする。現在の管理者名ハードコードと@humlablu.com除去処理を見直し、Firebase UIDと役割で管理できる形を目指す。まず開発用研究者（管理者）と開発用回答者を別々に登録し、本番の権限を自動継承させない。上松の基本アカウント名hiroki_uは維持可能だが、認証プロジェクトと資格情報を分ける。
4. Webは開発用Firebase、APIは同じ開発プロジェクトの資格情報、新規DBを使用。APIが別プロジェクトのトークンを拒否することを確認。秘密鍵はGitに入れない。画面に開発環境表示を固定する。
5. 配信準備の定期処理と通知送信フラグを分離。通知送信関数でも無効設定を強制する。DBはテストデータから作り、端末トークンは開発アプリのログイン時に新規登録する。本番トークン・未処理の本番配信予約をコピーしない。テスト開始は通知無効、通知テスト時だけ有効化する。
6. iOSにDev用Scheme/構成を追加。API URL、Bundle ID、GoogleService-Info.plist、表示名・アイコン・署名/Push entitlementをセットで固定。開発版は別Bundle ID・別App Store Connect登録にしてTestFlightへ。TestFlightの配布形式から環境を推測せず、ビルド時の設定で決める。TestFlightでもAPNs本番側の配布条件に合う署名・設定が必要。環境間でKeychain/共有コンテナー・キャッシュを共有しない。
7. AndroidもDev flavorと別applicationId、Firebase設定、API URL、表示名・アイコンを用意。既存AndroidはGoogle Play未公開なので、まず開発専用APK配布を想定し、Google Playテスト配布は別途判断。
8. ビルド時にAPI URL・Firebase project・アプリIDの組合せを検証し、不一致では失敗させる。通常利用者向けの本番/開発切替スイッチは設けない。App Store提出用は同じ検証済みソースから本番設定で生成し、開発アプリをそのまま本番として提出しない。
9. HTTPS公開・開発アカウント認証を確認し、下記の受入検証後に研究者へ案内する。TestFlight外部テスター向けに必要な審査・招待手順を完了し、有効期限（最大90日）より前に新ビルドを配布する。

## 公開前の受入検証

- 未認証アクセスでSurvey・利用者・回答が取得できない。開発トークン→本番API、本番トークン→開発APIが拒否される。
- 同じ端末に本番版とDev版を並べて置き、名称・アイコン・接続先・ログインが分かれる。
- devで作成→テスト利用者に予約配信→通知→起動→回答送信→Web表示→CSV/JSON出力まで確認。本番DB件数・配信予約・端末登録に変化がないことを確認。
- 通知無効でも配信準備と手動取得・回答が動く。通知有効時は開発端末だけに届く。
- JSTの日付境界・期限・再起動後の配信重複を確認。環境別バックアップ・復元・タイマーの対象を確認。
- API変更は旧本番アプリとの互換性もテスト。新機能に必要な最小アプリ版を記録する。

## 日常運用

研究者：dev WebとKIROKUN Devで作成・配信・回答を試す。実参加者のアカウントや実回答は使わない。確認済みSurveyは「設問テンプレートを保存」で持ち出し、本番Webの新規作成で読み込む。名前・通知文面・設問/分岐・対象者・配信日時を本番側で確認してから明示的に配信する。回答、アカウント、端末トークン、予約は移さない。本番DBと開発DBの自動同期は行わない。

開発者：開発環境で検証したコミット/テンプレート版と結果を記録。リリース前バックアップ、API互換性確認、対象環境の確認を行い本番へ反映。ロールバックするイメージを保持する。DB復元はバックアップ後の回答を失うため、コードの切り戻しと分けて判断する。

管理者：招待した研究者・回答者の権限を個別に管理し、不要になった開発アカウントを無効化する。TestFlight期限、証明書、バックアップ復元、環境別通知設定を点検する。開発DB初期化前に利用者へ周知し、再利用したいテンプレートを保存する。

## サーバー移行との関係

旧サーバー解約のための本番移行は別途進める。新サーバーに本番用の独立したCompose/DBを作り、最終同期時だけ旧本番の書込停止→バックアップ→復元→検証→既存ドメイン切替を行う。既存API URLと互換性を保てればサーバー移転だけを理由とするアプリ更新は原則不要。DNS切替前後の端末疎通と通知を確認し、切戻し期間を置いて旧サーバーを解約する。開発DBを本番へ昇格させない。
