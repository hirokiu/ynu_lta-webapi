# 複数プロジェクト所属・通知・データ分離

2026-09-18。設計案。現行アプリ/APIは未対応。今回のproto移行とは段階を分ける。

## 基本モデル

1人1アカウント（Firebase UID）に複数のプロジェクト所属を紐付ける。役割はプロジェクトごとに持つ。同じ人がAでは研究者、Bでは回答者、Cでは共同研究者でもよい。上松のプラットフォーム管理者は別の全体権限とする。アカウント、所属、現在表示中のプロジェクトを混同しない。

研究者個人ではなく研究プロジェクトをデータ分離単位にする。単独研究も共同研究も同じ仕組みで、所属人数だけが違う。所有者、共同研究者、回答者を定義し、研究者の招待権限や所有者移譲を明示する。最後の所有者は移譲せず脱退できない。プロジェクト所属の取消とアカウント全体の削除は別操作。

## アプリ（回答者）

管理画面は持たせず、1度認証した後に所属プロジェクトを選んで回答する。所属が1件なら自動で開き、複数なら選択・切替を表示する。招待リンク/コードから初期プロジェクトを選べる。ログイン時にプロジェクト名を毎回入力させる方式は任意の補助入力に留め、権限や認証の根拠にしない。名称は重複・変更し得るため内部は不変projectIdで扱う。プロジェクト名を知っているだけでは参加できない。

アカウント名ログインは前段のメール/ソーシャル方式と別途整合させる。projectIdと利用者名の組合せで別々の認証アカウントを作らない。

表示中のプロジェクトに関わらず、所属している他プロジェクトの通知を受信可能とする。回答途中で切り替える場合は下書きをprojectId/assignmentIdで分けて保存し、破棄しない。画面・キャッシュ・リクエスト・非同期レスポンスすべてにプロジェクトの文脈を持たせ、切替後に旧画面のレスポンスを混ぜない。

## Push通知

現行cloudMessage.service.tsはタイトル/本文中心でprojectIdや回答先IDを送っていない。UserSchemaはdeviceTokenが単一文字列で、複数端末・環境の登録を管理するモデルがない。サーバーと両アプリの変更が必要。

端末登録は共通管理側でUID・インストールID・FCM token・環境・通知設定を持つ。更新/ログアウト/アカウント切替/無効トークン削除に対応する。複数研究プロジェクトごとにFirebaseを作る必要はない。devとprotoの環境分離は維持する。

通知のdataには環境、projectId、assignmentIdまたは回答対象ID、notificationId、ペイロード版を含める。本文に回答内容等を入れない。通知ID/Android PendingIntent等を区別して別研究の通知が上書きされないようにする。送信時にも有効な所属と配信対象を照合する。

タップ後：アプリ起動→認証確認（未ログインなら目的地を保存してログイン）→サーバーで所属/対象者/期限を確認→必要ならプロジェクト切替を案内→正しい回答画面を取得。通知を信用して閲覧権限を付与しない。別人でログイン中なら内容を開かず案内する。退会・配信取消・期限切れなら説明して安全な画面へ戻る。任意URLや通知中のDB名へ接続しない。

前面/背面/終了状態、ログアウト中、別プロジェクト回答途中、複数通知、複数端末、遅延/重複、別アカウント、無効所属を実機検証する。Pushは到達保証や正本ではなく、アプリの取得APIで未回答を確認できるようにする。

## DB構成案

推奨候補：環境ごとにFirebaseを共有し、MongoDBには共通管理DBとプロジェクト別DBを置く。

|場所|内容|
|Firebase|本人認証・連携プロバイダー|
|共通管理DB|UID、確認済み連絡先、プロジェクト一覧、UID/projectId別の所属・役割・状態、招待、端末登録、サブドメイン対応、全体監査|
|プロジェクト別DB|Survey、配信、回答、研究用グループ、プロジェクト内参加者IDと属性|

所属にはUID+projectIdの一意制約。研究者には自研究の参加者IDを提示し、他研究への参加状況や共通UIDを不要に露出しない。連絡メール送信も共通基盤で所属検査を行う。

APIは認証→共通管理DBで有効所属/役割確認→登録済projectIdからDB解決→当該研究の対象レコード/回答者確認の順に処理する。サブドメインやリクエストのprojectIdだけでDBアクセスを許可しない。Mongooseの接続/モデルはDBごとに管理し、共有グローバル接続をリクエストごとに切替えない。接続プール/モデルキャッシュを無制限に増やさない。

DB別方式は研究単位の保存/バックアップ/削除を整理しやすいが、自動的な権限分離ではない。同じ管理資格情報・MongoDBプロセスなら操作ミス/資源障害の影響は共通。DB権限を絞り、必要な研究は別インスタンスへ隔離できるようにする。共通DBと研究DB間の招待受諾/所属変更等は冪等・再試行・整合性確認を用意する。現行standalone MongoDB 4.2でトランザクションを前提にしない。

比較：共有DB+全レコードprojectIdは運用/横断集計を簡素化するが全クエリに所属条件が必要。DB別は研究ごとの復元や隔離に適する一方、インデックス/スキーマ更新/接続/バックアップ対象が増える。現在の小規模想定では共通DB+研究別DBを第一候補とし、想定研究数・復元要求・将来のMongoDB版を確認して確定する。

プロジェクトDBだけの復元では所属/招待/監査が戻らないため、共通管理DBの関連レコードと整合する復元計画を用意する。研究者がDB名・資格情報を直接指定する機能は設けない。

## 研究者Web

ログイン後に自分のプロジェクト一覧（単独/共同、役割）を表示。研究サブドメインを開いた場合も所属を確認。上部に研究名・役割・切替を常時表示し、招待・配信・削除・エクスポートは対象プロジェクトを明記する。別タブでA/Bを同時に操作できるよう、サーバー上の「最後に選んだ研究」だけに依存しない。各リクエストにprojectIdを固定する。招待・新規プロジェクト作成は許可された研究者だけに提供する。

## 移行順

今回のproto移行では既存資産を1つの既存プロジェクトとして保持する。複数研究へ既存データを自動分類しない。将来、UID対応→共通所属モデル→APIの研究境界→研究別DB/既存研究移行→研究者切替UI→アプリ切替/通知の順で実装する。移行期間中の旧APIは既存研究に固定し、新規の複数研究へ曖昧にルーティングしない。

受入条件：研究AのIDでBの回答取得/更新/出力が不可、研究者/回答者の複数所属、複数タブ/端末の独立、通知の正しい遷移、所属取消の即時反映、部分失敗からの復旧、研究単位のバックアップ復元を検証する。
