protoは破棄前提の空データ環境ではなく既存資産の継続先。devの試行データをprotoへ自動同期しない。設問はテンプレートで持ち運ぶ。protoで実参加者と回答が動く場合は、プロトタイプという名称でもバックアップと権限管理が必要。

## Firebase / DBの分け方（推奨案・未決定）

- proto：既存Firebaseプロジェクトを維持しUIDと既存認証を引き継ぐ。DBは旧サーバーの最終バックアップから新サーバー専用ボリュームへ移行。
- dev：新Firebaseプロジェクトと空の独立DBを推奨。開発端末の通知登録・認証操作がprotoに影響しない。既存Firebaseを暫定共有する場合は認証変更・端末トークンの干渉が残るため、完全分離とは呼ばない。
- 将来の正式プラットフォーム：独立した本番Firebase / DBを検討。研究者・プロジェクトごとにFirebaseを必ず新設するという意味ではない。1本番認証基盤内で所属と役割を管理する案と、個別隔離が必要な研究を分ける案を比較する。

## データを保持する認証移行

1. Firebase認証ユーザーとMongoDBをバックアップし、Firebase UID → 既存userIdの対応表を作る。一対一を検証し、重複・欠落・外部ドメイン管理者は個別に解決する。対応表やメール一覧はGit/チャットへ記録しない。
2. APIにUID対応層を先行導入。既存のhiroki_u等の業務上の利用者ID、Survey/配信/回答の内部IDを維持する。rolesもUID側で管理する。未知UIDをメールの前半一致だけで既存利用者へ自動接続しない。
3. 新しいログイン形式を決める。研究者は受信できる実メールで招待/再設定できる方式を第一候補とする。回答者の利用者名ログインを維持するなら、安全な認証入口を設計する。所有するKIROKUN配下の内部メールに置換する簡易案は可能だが、メール依存や再設定・招待メールの課題は残る。架空メールを招待先に使わない。
4. Web・iOS・Androidを更新して旧ドメインの付加/除去をなくす。画面/エラー/ヘルプ/通知/出力ファイルに旧名が出ないことを確認。開発版は別ID、protoの既存配布アプリは更新として提供する。
5. 移行テスト用アカウントでFirebase UIDを変えずにemailを更新。パスワードを新規保存/配布し直すことは前提にしない。再ログインとセッション更新が必要になる可能性を扱い、既存回答取得/新規回答/グループ/CSV/権限を照合する。
6. 協力者に更新と切替時間を案内し、既存protoアカウントを順次または計画停止で切替。旧アプリは旧メールを付加して直接Firebaseへログインするため、サーバーだけで救済できない。旧アプリ対応期間中は旧認証を残すか、完全除去と同時に更新必須とする。新旧の別UIDを安易に作って同じ利用者に結び付けない。
7. 対象者の更新/再ログイン成功を確認してFirebaseの現役ユーザーメールと設定から旧ドメインを除去。protoの稼働ソース/ビルドからも除去。過去Git履歴・バックアップは履歴としてアクセス制限して保持し、破壊的な履歴改変や保全データの削除は別判断。
8. 新規ユーザーは最初から新方式で追加。研究者による回答者招待・追加、上松の全体管理という権限方針を維持する。proto用の最小限のユーザー追加機能は完全なプラットフォーム化を待たずに実装対象に含めるが、権限検査・重複防止・所属/配信先作成を備える。

Firebase Admin SDKはUIDを指定したemail更新に対応する。ドメインだけの削除で有効なメールになるわけではないため、メール/パスワード方式を継続するなら移行先メールが必要。代替認証を選ぶ場合は別途実装・検証が必要。

## 今回の移行順序

1. 上記UID対応と新ログインの実装・検証、採用するFirebase構成と新ログイン方式の確定。
2. 新サーバーにprotoを用意し、既存資産のコピーで共同研究者が確認。コピー段階はアプリ非連携/通知停止を明示し、稼働開始後のprotoと区別する。上松専用devは別途作成する。
3. 旧サーバーの書込/定期処理停止、最終バックアップ、proto復元、ドメイン/旧API互換接続の切替。認証切替とアプリ更新の段取りを合わせる。
4. 既存参加者の過去データ・再ログイン・配信/回答、新規参加者の登録、権限とバックアップ復元を確認してproto運用開始。
5. 観察期間と旧サーバー依存の確認を経て旧dev.alchembright.comサーバーを解約。旧APIホスト名は必要なら新サーバーで継続する。

## 将来のサブドメイン運用

wwwを入口とし、proto/dev/www/admin等の予約名を確保。研究者/プロジェクトのサブドメインは登録済みの対応表で解決する。URLだけで権限を与えず、APIでUID・所属・役割を検証。認証Cookieを全サブドメインへ無条件共有せず、認証フロー/CORS/招待リンク/証明書発行/名前変更を設計する。研究者が複数プロジェクトを持つ場合や、回答者が複数研究に参加する場合も扱う。ワイルドカードDNSを設定するだけではマルチテナント化は完了しない。
