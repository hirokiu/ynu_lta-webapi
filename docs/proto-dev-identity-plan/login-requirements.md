# ログイン・連絡先・アカウント復旧の追加要件

2026-09-18。利用者要望に基づく仕様。実装・プロバイダー登録・メール送信は未実施。

## 認証と連絡先を分ける

メール＋パスワード、Google、GitHub、LINEを提供する。本人識別はFirebase UID、研究データとの接続は既存userIdとの対応、研究参加はproject membershipで扱う。連絡用メールを別属性として保存し、確認リンクで所有確認を完了してから参加・調査利用を開始する。メールのないソーシャルアカウントでも受信できるアドレスを追加入力できる。

ソーシャルログインのメールと連絡用メールは異なってよい。未提供/未確認のアドレスを連絡可能とみなさない。連絡先変更時は新アドレスを検証してから確定し、必要に応じ再認証と旧アドレスへの変更通知を行う。バウンス等で到達不能になった場合は再確認を促す。確認済みであっても永続的な到達保証はない。

Appleの非公開メール転送も受信できる連絡先として扱い、実アドレスの開示を強制しない。送信元のリレー登録など到達条件を整える。

## プロバイダー

- メール/パスワード、Google、GitHub：Firebaseの対応プロバイダーを使用。必要なアプリ/OAuth設定と最小スコープを用意する。GitHubはメールを必ず得られる前提にせず、連絡先追加入力に対応する。
- LINE：LINE Loginのチャネル登録とトークン検証を実装。メール取得には事前申請と利用者の許可が必要。Firebaseとの接続は、Identity PlatformのOIDC対応を使えるか実際の仕様/互換性・費用を検証するか、サーバーでLINEのトークンを検証してFirebaseカスタムトークンを発行する。未検証のLINEユーザーIDを信用しない。OIDCで無条件に接続できると断定しない。
- iOSのソーシャルログイン追加時はApp Review 4.8の適用/例外を確認し、Sign in with Appleも原則設計に含める。
- protoとdevでOAuthリダイレクト先・設定・秘密情報を管理する。秘密はクライアントやGitに含めない。

## 既存利用者と複数ログイン

既存UIDを維持して旧userIdとの対応を固定する。既存アカウントにログインまたは個別の本人確認をした後、確認済み実メールとGoogle等を連携する。メール文字列が一致するだけでアカウントや研究データを自動統合しない。別UIDで先に登録してしまった場合は自動で回答を移さず、所有確認を伴う復旧手順にする。最後のログイン手段を解除してアカウントに入れなくなることを防止する。

humlablu.com除去時は新しいWeb/アプリへの更新・再ログインを案内し、対応表を維持した状態でメールを変更する。旧メール宛に確認/再設定メールを送って本人確認したことにしない。受信可能なメールが未登録の既存参加者には、安全に新連絡先を登録する移行導線を用意する。

## パスワード再設定

メール/パスワード利用者にFirebaseの期限付き再設定リンクを送る。日本語メールとKIROKUNの戻り先を設定し、登録有無を推測できない案内・送信回数制限を設ける。

ソーシャル専用利用者にKIROKUNのパスワードがあるとは限らない。Google等の認証情報の復旧は各サービス側で行う。希望者がKIROKUNのメール/パスワードも追加する場合は、ログイン済みの同一UIDへ再認証・メール所有確認を伴って連携する。連絡用メールを変更しただけでログイン/復旧権限が自動移転する設計にはしない。

## 招待・連絡

研究者→自分のプロジェクトの参加者、上松→研究者のメンテナンス連絡を可能にする。Firebaseの認証メールと研究連絡メールは用途を分ける。後者は送信サービス、送信ドメイン認証、配信キュー、再試行、到達状況、送信履歴を用意する。受信者のアドレスを他の参加者に露出させない。研究者に他研究の宛先を提供しない。ログイン用OAuthトークンをメール送信権限に流用しない。

招待メールはプロジェクト・宛先・役割・期限に紐付ける。別メールのソーシャルアカウントで受諾する場合も、招待先メール所有を確認してから所属を追加する。ログイン成功だけで研究者/回答者の権限は付与しない。重要な運用連絡、研究参加に必要な連絡、任意のお知らせを分けて通知設定を設計する。

## 実装順と受入条件

1. UID対応・役割・確認済み連絡先・既存利用者の移行導線。
2. メールログイン/確認/再設定とGoogle、iOSのApple対応判断。
3. GitHub/LINE追加、同一UIDへの連携・解除・復旧。
4. 招待・研究連絡・メンテナンス連絡の管理画面と配信履歴。

各方式で過去回答が維持されること、メール未取得/非公開/未確認/変更、期限切れ招待・再設定、アカウント競合、別研究へのアクセス拒否、devからprotoへ影響しないことを検証する。これらは実装順であり、GitHub/LINEの要望を取り下げるものではない。
