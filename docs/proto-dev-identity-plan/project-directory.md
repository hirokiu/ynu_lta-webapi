# プロジェクト名・ディレクトリ・所属API設計

2026-10-12。ユーザー指定に基づく設計。以下のAPI名とJSONは提案であり未実装。既存Protoの認証・配信や共同研究者向け確認ビルドは変更しない。

## 決定方針

- 表示名は管理画面で編集し、サーバーを正本としてiOS/Android/Webが取得する。名前の変更だけでアプリ再配布を要しない設計に移行する。
- 不変のprojectId、変更可能なdisplayName、管理画面URL、API接続先、認証環境は別項目とする。表示名変更でURL・DB・UID・所属・回答を変更しない。
- 全プロジェクト一覧を未認証で公開しない。公開ディレクトリと本人の所属一覧を分離する。管理者だけが非公開を含む全件を取得できる。
- 認証と所属管理は共通の論理APIとして分ける。当初は同じサーバー/デプロイ内のモジュールでよく、別サーバーは必須ではない。Firebaseは本人認証、共通APIは所属・役割・接続先解決を担当する。
- Devは独立した認証・DB・ディレクトリ。配布版にDevを列挙せず、切替で環境を越えない。

## JSON/API契約案

公開GET /platform/v1/projectsはpublicの稼働プロジェクトだけを返す。JSONファイルを手編集するのでなく、管理DBからJSONレスポンスを生成する。小規模導入で静的JSONを使う場合も同じスキーマ・公開範囲を守る。

```json
{
  "schemaVersion": 1,
  "revision": "1",
  "projects": [
    {
      "projectId": "proto",
      "displayName": "Proto",
      "adminWebUrl": "https://proto.kirokun.alchembright.com",
      "apiBaseUrl": "https://proto.kirokun.alchembright.com/api/",
      "authRealm": "proto"
    }
  ]
}
```

これはスキーマ例であり、Protoをpublicに公開する決定ではない。Protoの公開一覧への掲載は初期値privateとし、現在のアプリにある既知のProto接続先から互換導線を保つ。公開JSONにメール・所属者・回答・秘密鍵・内部DB名を含めない。

認証後GET /platform/v1/me/projectsは検証済みUIDの有効所属だけを返す。public/privateを問わず自分のプロジェクトを列挙し、本人のroleとstateを追加する。所属一覧の応答は共有キャッシュ禁止。研究者に他人の所属一覧は提供しない。

GET /platform/v1/projects/:projectIdは公開可能な情報、または所属確認済みの情報だけを返す。非公開の未所属アクセスは存在を判別できない同一の応答とする。公開プロジェクトでも公開なのは紹介情報のみで、Survey/回答APIには所属・対象者・役割検査が必要。

PATCH /platform/v1/projects/:projectId/settingsは許可されたプロジェクト管理者がdisplayName（1〜80文字、前後空白除去、プレーンテキスト）と任意の概要を更新する。revisionの一致を必須にして競合は409。変更者・時刻・変更前後を監査記録。一般研究者/回答者に設定変更を許可しない。公開範囲変更は別権限・明示操作とする。

adminWebUrl/apiBaseUrl/authRealmは上松の全体管理機能だけで設定。研究者の名称編集と接続先変更を混同しない。サーバーが登録・検証したHTTPS接続先のみを許容し、任意入力URLやリダイレクト先へ認証トークンを送信しない。管理画面URLからAPI URLを推測せず明示設定を使う。

## ログイン順序と互換性

将来の標準：固定の信頼済み共通認証先でログイン → /me/projects → 選択 → 対象APIがトークンと所属・役割を検証 → Survey一覧。1件なら自動選択。0件なら参加案内を表示し、勝手に所属を作らない。

公開ディレクトリ・研究専用URL・招待から先にプロジェクトを選ぶ経路も提供できる。その場合も認証先は信頼済みauthRealmから決定し、ログイン後に所属を再検査する。プロジェクト名/URLを知ることを参加権限としない。

現行Protoのユーザー名+パスワード方式は当面維持する。先に固定Protoで認証した後、単一プロジェクト情報を取得する互換経路を設ける。共通認証への移行では既存UID/研究内userIdの対応を保全する。新規ユーザー名重複は内部の不変accountIdで識別し、旧式の名前ログインにはprojectId/authRealmで名前空間を限定する。将来の共通メール/Googleログインは1本人に複数所属を結び付ける。異なるFirebaseのアカウントをメール一致だけで自動統合しない。

## 非公開プロジェクト

初期はpublic/privateの2種類。privateは公開一覧・検索・件数から除外し、所属者の一覧と認証済み招待受諾経路だけに表示。招待は期限付き単回トークン、取消可能、所属と役割をサーバーで決定する。リンクに任意API URLや秘密情報を埋め込まない。未ログイン画面では研究名を不用意に表示しない。

ログアウトで所属キャッシュを削除。所属取消後は各研究APIで拒否し、キャッシュが残っても取得できない。通知送信時とタップ時にも所属を検査し、通知本文に非公開研究名を含めるかは別の通知公開方針として設定する。公開範囲をprivateへ変更した場合は公開一覧キャッシュを無効化するが、過去に公開された名称の回収までは保証しない。

## アプリ表示・障害時

起動/前面復帰/プロジェクト選択時に名称とrevisionを取得。公開情報はETagで再検証、所属情報は認証付き再取得。ネットワーク不通は直近の名称をキャッシュ表示し、サーバー由来の空値/不正レスポンスで名前を消さない。初回失敗の互換既定値はProto/Dev。名称取得失敗だけで認証失敗と表示しない。

選択キー・回答下書き・通知先解決にはdisplayNameでなくprojectIdを使う。同名プロジェクトがあっても識別可能な概要を併記する。長い名前・日本語・英語・最小画面を検証。多言語表示名は将来displayNamesの言語別辞書として追加可能にし、初期displayNameをフォールバックにする。

## 段階実装と受入条件

1. 単一Protoの管理者用名称設定、認証後のプロジェクト情報取得、Web/iOS/Android表示の動的化。既存UID/回答/URLは維持。新アプリを上松のみへ配布して確認後、共同研究者へ手動配布。旧アプリでは旧表示名が残る。
2. 共通プロジェクト台帳・所属モデル・共通認証導線・公開/所属一覧。研究境界を全APIで検査し、別プロジェクトデータへの取得/変更/出力を拒否する試験を先に整備。
3. 新規プロジェクト開設、研究別DB/管理画面URL、private招待、アプリの複数所属切替と通知。DB分離だけを権限分離とみなさない。

必須試験：改名で既存回答/ログイン/Pushが維持、設定権限拒否、更新競合、通信失敗時の表示、privateの匿名列挙不可、所属取消、名前空間衝突、他研究のID差替え拒否、任意接続先へのトークン送信拒否、Dev/Proto越境拒否。現行の単一deviceTokenから複数端末管理への移行も別途必要。
