# KIROKUN：更新手順の一本化と取得処理の改善

2026-09-17。稼働版タグ `production-baseline-2026-09-17` を保存したまま実装。
本番のDB、コンテナー、タイマーにはこの変更をまだ適用していない。

## 構成

フロント/API/MongoDBの3サービスを維持する。APIリポジトリを運用の入口にし、`webapp` submoduleでフロントのコミットを固定する。APIの1コミットで、対応するWebソースとCompose・更新スクリプトを再現できる。2リポジトリの履歴を壊さず、配備単位を一本化する方式。コンテナー内の直接編集は不要。

```
ynu_lta-webapi/
  src/                 API
  webapp/              固定コミットの ynu_lta-webapp
  compose.yaml         Web / API / MongoDB
  ops/manage.sh        build / deploy / backup / restart / indexes / status
  ops/verify-backup.sh バックアップ復元検証
```

`git clone --recurse-submodules`で取得し、`.env.example`を`.env`へコピーして設定。秘密鍵はリポジトリ外のファイルをDocker secretとして渡す。DB/APIのポートは外部公開しない。Webは初期設定で127.0.0.1:8080のみ。通知は検証環境で誤送信しないよう初期値false。

Linux + Docker Compose v2（`up --wait`対応）、Git、bash、flock、gzip、sha256sumを使用する。

## 更新

```sh
git pull --ff-only
git submodule update --init --recursive
# .envのRELEASE_IDをそのリリース固有の値にする
./ops/manage.sh deploy
./ops/manage.sh status
```

`deploy`は固定済みソースからイメージ作成→稼働中ならバックアップ→起動・ヘルスチェック、の順に処理する。tarファイルの手動受け渡しは不要。過去のイメージは自動削除しない。コードが未コミットなら配備を拒否する。RELEASE_IDは使い回さない。APIの健康状態はDB接続も確認する。日次バックアップ・週次再起動はイメージ再作成や新設定の配備を行わない。

`docker-compose.yml`は稼働版の記録として残すが、更新では明示的に`compose.yaml`を使う。新Composeのデータ領域は新しい名前付きボリュームであり、旧`/data/git/lta-webapi/db/surveyDBData`を自動的に引き継がない。

## 初回移行と切り戻し（本番で実行する前に必要）

1. 別のComposeプロジェクト名・ポートで検証環境を起動する。通知false。DBの古い物理ファイルを直接共有しない。
2. 旧APIを停止した状態で旧MongoDBを`mongodump --db Survey --archive --gzip`で取得し、コレクション件数を記録。旧APIの再開は失敗時にも行う。本番データをMac/GitHubに置かない。
3. 同じサーバーの新MongoDBへ復元し、件数・索引・CSV・ログイン・モバイルAPI互換性を検証。`ops/verify-backup.sh /absolute/path/archive.gz`で隔離復元も確認する。
4. `./ops/manage.sh indexes`で非ユニーク索引を明示作成する。API起動時の自動索引作成は無効。
5. 本番切り替え時は旧API停止→最終バックアップ→新DBへの最終復元→通知設定を本番用にする→Web/APIの接続先を切り替える。旧・新APIから同時に通知を送らない。
6. 新規書き込みを受ける前なら、旧コンテナーへ戻せる。新DBで書き込み後は旧DBへ単純に戻すとデータが欠落するため、書き込みを止め新DBを保持し、同じDBに対する前版コードへの切り戻しを検証して行う。

TLS・ドメイン・既存モバイルの接続先（旧ホスト名も含む）は切り替え時に維持する。Compose単体はHTTPであり、TLS終端は既存構成との調整が必要。空の新DBを本番公開しない。

## バックアップと定期再起動

- 承認済みの初期時刻：毎日03:00 JSTバックアップ、日曜03:30 JSTバックアップ後に全コンテナー再起動。保存期間は初期30日。
- `ops/kirokun-*.service`と`.timer`は`/opt/kirokun`配置を想定したsystemdテンプレート。`ops/schedule.conf`で時刻・保存日数・取得間隔・実行ユーザー（Docker権限が必要）を変更し、`sudo ./ops/install-timers.sh`で反映する。まだ有効化していない。
- 現MongoDBはstandaloneなので、`mongodump`中の整合性を保つため唯一の書き込み元であるAPIを停止する。停止中はモバイルの送受信も一時的に失敗する。所要時間を検証環境で測り、予定時間を決める。
- DBを外部公開せず、別の書き込み元がないことが前提。レプリカセット化・oplog付きバックアップは今後、停止時間を避けるための候補。
- gzipアーカイブ・SHA-256・コレクション件数を`backups/`に保存。権限は所有者限定。途中失敗時はAPIを再開し、不完全ファイルを削除する。flockで配備・バックアップ・再起動を直列化する。
- 再起動順はAPI停止→DB再起動・応答確認→API開始→Web再起動・健康確認。再起動はクエリ改善の代替ではない。
- 保存日数は`BACKUP_RETENTION_DAYS`（7、10、30等）。新しいバックアップ成功後、保存期間内の復元検証済みマーカーがある場合に限り、期限切れのこのアプリのバックアップを削除する。復元検証を継続しない場合は安全のため削除を止める。別ホストへの暗号化バックアップ先、空き容量監視、失敗通知先は本番有効化時に決める。同じサーバーのバックアップだけではサーバー障害に備えられない。
- `verify-backup.sh`はネットワークを持たない一時MongoDBへ復元し、コレクション件数を照合、終了時にそのコンテナーと匿名ボリュームを削除する。データ内容の完全一致・業務上の正しさを保証する検証ではない。

## 取得処理の変更

|対象|変更|
|---|---|
|管理一覧|新しい管理者専用ページAPI。初期50件、最大100件、次ページ有無のみ取得（毎回全件数集計しない）|
|管理画面|Survey一覧・Assignment一覧・Survey詳細の配信一覧をページ分割。古い通信の応答で新しい表示を上書きしない|
|一覧の転送量|必要な表示項目と設問IDだけを取得。設問本文・回答本文を一覧に送らない|
|検索|配信一覧ではSurvey名・利用者・グループを検索。期間条件と検索条件を併用。検索語は正規表現の特殊記号として扱わない|
|利用者別API|該当利用者の回答だけをDBで絞る。二重ループをID対応表に置換。既存モバイルのレスポンス構造は維持|
|回答エクスポート|最初に配信IDだけ取得。回答なしを除外しleanで読み込む。任意期間フィルター（lastOpenedAt、なければupdatedAt）|
|大量エクスポート|1万件を超える場合は413で期間指定を求める。黙って切り捨てない。全件のストリーミング出力・非同期ジョブは今回未実装|
|CSV|稼働版の日本語列名・日本時間・複数選択列展開を維持。回答本文/CSVのログ出力を削除|
|ダウンロードUI|期間指定・エラー表示・生成中表示。長いdata URLをBlob URLに変更し、再生成・離脱時に解放|
|接続|Webから同一オリジンの`/api`を利用。研究者別サイトへの展開でAPIホスト名の埋め込みが不要|

索引は`ops/indexes.js`参照。全件取得APIは互換性のため残しているため、利用者/グループ詳細等の追加最適化余地はある。部分一致検索そのものは索引で全面的に高速化できるものではない。

## MongoDBの限界か

稼働環境で確認したSurvey56、配信4,182、回答4,651件と、`_id`以外の索引がない状態から、まず全件読み出し・索引・照合処理を直す判断。DB製品の限界という証拠はない。ただしサーバーの約1GBメモリ、旧MongoDB/ドライバー、データ増大などは別途考慮が必要。本番の応答時間や実行計画を測定して改善率を評価する。

## 検証と残課題

- Node 22によるAPI/WebのDockerビルドに成功。APIの欠落していたMongoDB型定義を固定し、TypeScriptビルドを復旧。
- 合成データの統合テスト：認証、ページ境界、重複なし、検索特殊文字、期間指定、CSV互換性、利用者別回答を確認。
- 合成120配信で索引前は120文書走査、索引後は対象110文書走査＋IXSCANを確認。本番の速度改善倍率を示すベンチマークではない。
- UIの応答競合、ダウンロード失敗後の表示復帰をテスト。
- 合成123文書をmongodumpし、隔離コンテナーに復元、コレクション件数を照合。
- バックアップ失敗時のAPI再開・期限切れ削除・再起動順序をDockerモックで検証。さらにLinuxの実スクリプトでComposeのバックアップ・全再起動・隔離復元を通して検証。3サービスの健康確認に成功。systemdタイマーの実運転は未実施。
- Vue 2、旧Mongoose/Firebase SDK、MongoDB 4.2は今回の互換性優先段階では残る。依存の脆弱性警告、Webバンドルサイズ警告があり、全面更新完了ではない。次段階でライブラリ更新とMongoDBの段階移行を行う。

参考： [Docker Composeの本番運用](https://docs.docker.com/compose/how-tos/production/)、[MongoDB mongodump](https://www.mongodb.com/docs/database-tools/mongodump/)。

設定例：毎週は`BACKUP_ON_CALENDAR="Sun *-*-* 03:00:00 Asia/Tokyo"`、毎月は`"*-*-01 03:00:00 Asia/Tokyo"`、正確な10日間隔は`BACKUP_INTERVAL="10d"`（時刻固定と別方式）。保存日数だけの変更は次回から反映され、タイマーの再インストールは不要。時刻・取得間隔を変えた場合はインストールスクリプトを再実行する。
